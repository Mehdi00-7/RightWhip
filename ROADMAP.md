# AutoTrail — Build Roadmap

A Rightmove-style used-car marketplace, built phase by phase as a learning project.

**Stack:** Next.js 15 (App Router, TypeScript, Tailwind) → FastAPI (Python) → PostgreSQL
**Method:** I explain the concept and show the shape of the code; you write it; I review and correct.

---

## Ground rules for how we work

1. **One phase per session.** Don't jump ahead — each phase assumes the last one works.
2. **You type the code.** I'll explain the concept, show a skeleton or a worked example of *one* case, and you write the rest. Then paste it back / tell me to review.
3. **Every phase ends with a demo.** If you can't show it working in a browser or in `/docs`, the phase isn't done.
4. **Commit at the end of every phase.** Message format: `phase-N: <what works now>`. Your git history becomes the story of the project on your CV.
5. **When stuck for >20 min, ask.** Struggling is how it sticks; grinding is not.

**Why two services?** It forces you to think about the API contract explicitly — what the frontend is allowed to ask for, what the backend promises to return. That boundary is the single most transferable thing in this project.

## Phase 1 — Data model & first listing (1 day)

**Goal:** create a listing via the API docs page, then read it back.

| Step | What you build | Concept |
|---|---|---|
| 1.1 | SQLAlchemy models: `Seller`, `Listing`, `ListingImage` | ORM; foreign keys; one-to-many |
| 1.2 | Alembic init + first migration | Migrations as version control for your schema |
| 1.3 | Pydantic schemas: `ListingCreate`, `ListingRead` | Why the DB model ≠ the API shape |
| 1.4 | `POST /listings`, `GET /listings/{id}` | Dependency injection for the DB session |
| 1.5 | Create + read a listing via Swagger UI | Reading a 422 validation error properly |

**Listing fields (decide these now, they shape everything after):**
`id, make, model, variant, year, price, mileage, fuel_type, transmission, body_type, colour, doors, engine_size, description, postcode, latitude, longitude, seller_id, status, created_at`

**Watch out:** store price in **integer pence/pounds**, never a float. Floats and money don't mix.

## Phase 2 — Synthetic seed data (½ day)

**Goal:** ~500 plausible listings in the database.

Write `api/scripts/seed.py`. The interesting part is making the data *realistic*, because your fair-price feature later is only as good as the data underneath it:

- Price depreciates roughly exponentially with age (~15–18%/year from a per-model new price)
- Mileage ~ 8,000–12,000/year with noise
- Higher mileage → lower price, on top of age
- Cluster lat/lng around real UK city centres so map + radius search have something to show

**Do not scrape AutoTrader/Rightmove.** Generate it. Say so in your README — "synthetic dataset generated by `scripts/seed.py`" reads as good judgment to a reviewer.

## Phase 4 — Filters & search (1–2 days) ⭐ core

This is the backbone of the whole product. Take your time.

| Step | What you build | Concept |
|---|---|---|
| 4.1 | Query params on `GET /listings`: make, model, price_min/max, year_min/max, mileage_max, fuel_type, transmission | Optional params with sane validation |
| 4.2 | A **query builder** in `services/search.py` that composes SQLAlchemy filters conditionally | The single most reusable piece of code in this project — Phase 9's AI plugs straight into it |
| 4.3 | Filter sidebar in Next, state stored in the **URL** (`useSearchParams`) | Shareable/bookmarkable filtered searches; back button works |
| 4.4 | Indexes on `(make, model)`, `price`, `year`; `EXPLAIN ANALYZE` before/after | Reading a query plan; what an index actually does |
| 4.5 | Result count + active filter chips | |

**Design the query builder so it takes one `SearchFilters` Pydantic object.** Then dropdowns and the AI both produce the same object, and there's exactly one code path to the database. Do this and Phase 9 is an afternoon; skip it and Phase 9 is a rewrite.

## Phase 9 — AI #1: Natural language search (1 day) ⭐ headline feature

**Goal:** type *"reliable family car under £15k, low mileage, automatic"* → correct filters applied.

```python
# api/app/services/nl_search.py
from anthropic import Anthropic
from pydantic import BaseModel, Field

class SearchFilters(BaseModel):          # the SAME object Phase 4's builder takes
    make: str | None = None
    price_max: int | None = Field(None, description="Max price in GBP")
    mileage_max: int | None = None
    transmission: str | None = None
    body_type: str | None = None
    # ...

client = Anthropic()
resp = client.messages.parse(
    model="claude-opus-5",
    max_tokens=1024,
    system=SYSTEM_PROMPT,               # domain rules: valid makes, "family car" -> estate/suv/mpv
    messages=[{"role": "user", "content": query}],
    output_format=SearchFilters,        # structured output — guaranteed schema
)
filters = resp.parsed_output            # a validated SearchFilters instance
```

| Step | What you build | Concept |
|---|---|---|
| 9.1 | `SearchFilters` as the shared contract | One schema, two producers (form + LLM) |
| 9.2 | `messages.parse()` with `output_format` | **Structured outputs** — schema-guaranteed JSON, no regex parsing |
| 9.3 | A system prompt encoding domain rules | Prompt design: what only *you* know (your valid makes, your body types) |
| 9.4 | Validate against real DB values; drop unknown makes | Never trust model output straight into a query |
| 9.5 | Show interpreted filters as editable chips | Trust: the user sees and can correct the interpretation |
| 9.6 | Cache identical queries; graceful fallback to keyword search | Latency, cost, and failure handling |

**Talking point for interviews:** *"the LLM never touches SQL — it produces a validated Pydantic object that feeds the exact same query builder as the dropdowns."* That's the answer that separates a demo from an engineer.

## Phase 11 — AI #3: Listing assistant (stretch, 1 day)

Seller uploads photos + basic details → Claude drafts a description and flags visible damage.

- Vision: pass images as base64 `image` content blocks alongside a text block
- Structured output again: `{ description: str, highlights: list[str], damage_flags: list[str] }`
- **Guardrails:** the model must not invent specs — pass make/model/year/mileage as facts and instruct it to use only those
- The draft is always editable before publish. Never auto-publish generated copy.
